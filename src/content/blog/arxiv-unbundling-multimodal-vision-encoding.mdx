## The Gap

How Multimodal Large Language Models (MLLMs) should ingest visual inputs is the most contested architectural debate in foundation models:
- **Mainstream Recipe (e.g., LLaVA, Qwen-VL, Pixtral)**: Prepends an independently pretrained Vision Transformer (e.g., CLIP, SigLIP, DINOv2) to extract patch tokens before projecting them into a frozen or fine-tuned language backbone.
- **Joint Training Recipe (e.g., Chameleon, PaLI)**: Keeps a separate vision encoder but trains it from scratch concurrently with the language backbone.
- **Encoder-Free Recipe (e.g., Fuyu, Gemma 3)**: Discards the vision encoder entirely, feeding raw linear patch embeddings directly into the shared autoregressive transformer.

Comparing these paradigms across published models has historically been impossible because existing models differ across data distributions, training recipes, tokenizers, and parameter budgets. 

Crucially, the authors observe that **standard vision encoders bundle three orthogonal design choices**:
1. **The Visual Prior**: Learned representations imported from upstream pretraining (e.g., contrastive language-image learning).
2. **Dedicated Vision Capacity**: A block of parameters allocated exclusively to processing vision tokens without parameter competition from text.
3. **Pre-Fusion Placement**: Placing this visual capacity strictly *before* the multimodal fusion boundary (the first layer where vision and text interact).

```
                  THE THREE BUNDLED CHOICES OF VISION ENCODERS

  [Standard Pretrained Vision Encoder (e.g. CLIP / SigLIP)]:
  Image Patches ──> [Pretrained ViT (0.4B)] ──> Projector ──> [Multimodal Backbone]
                    ├─ 1. Upstream Visual Prior?  (CLIP pretraining)
                    ├─ 2. Dedicated Vision Capacity? (0.4B vision-only params)
                    └─ 3. Pre-Fusion Placement?  (Runs entirely BEFORE text fusion)

  The Critical Question: Which of these three choices actually drives performance?
                         Can we eliminate the separate encoder without sacrificing quality?
```

## The Increment

**One sentence**: Through a strictly controlled, lifetime-compute-matched framework spanning backbones from 0.6B to 6.4B parameters, the authors prove that **upstream visual priors provide zero benefit over joint training from scratch**, but **dedicated vision capacity is mandatory**; crucially, this capacity can be relocated **in-fusion into the first 8 layers of the language backbone**, matching pre-fusion encoders while collapsing the dual-model serving stack and slashing Time-To-First-Token (TTFT).

```
                      UNBUNDLING THE VISION ENCODER PARADIGM

  Question 1: Is Upstream Pretraining Needed?
  [Pretrained Encoder] vs [Scratch Encoder] (Matched Lifetime FLOPs)
  ──> Result: From-scratch encoder MATCHES or BEATS pretrained encoder!
              Pretraining FLOPs are better spent directly on multimodal training.

  Question 2: Is Dedicated Vision Capacity Needed?
  [Scratch Encoder (1.7B + 0.4B)] vs [Encoder-Free (2.1B Unified Backbone)]
  ──> Result: Encoder-free trails badly on VQA (-5.4% at 1.7B, requires 3.0x-4.4x FLOPs).
              Vision tokens demand dedicated parameters!

  Question 3: Must Capacity Precede Multimodal Fusion?
  [Pre-Fusion Encoder (0.4B)] vs [In-Fusion Vision Modules in Layers 1-8]
  ──> Result: In-fusion matches separate encoder across all VQA benchmarks,
              unifies the serving runtime, and reduces Time-to-First-Token (TTFT)!
```

## Core Framework & Experimental Protocol

### 1. The Lifetime Compute-Matched Protocol
To eliminate confounding variables, every model is trained from scratch on common data:
- **Text Data**: Nemotron-CC v2/v2.1.
- **Image-Text Data**: MetaCLIP 1.2 English pairs (re-captioned using Qwen2.5-VL-32B).
- **Multimodal Data Ratio**: 70% text, 30% image-text.
- **Lifetime Compute**: Every comparison strictly matches the **cumulative FLOPs** of all training stages (including upstream encoder pretraining).

```
                    COMPARISON OF THE FOUR DISENTANGLED RECIPES

  Recipe                 Visual Prior?   Dedicated Vision Capacity?   Pre-Fusion Placement?
  ─────────────────────────────────────────────────────────────────────────────────────────
  1. Pretrained Encoder      YES                    YES                       YES
  2. Scratch Encoder         NO                     YES                       YES
  3. Encoder-Free            NO                     NO                        NO
  4. In-Fusion (Proposed)    NO                     YES                       NO (Layers 1-8)
```

### 2. Dissecting the Three Choices

#### Choice 1: Upstream Visual Prior vs. From-Scratch Training
The authors compared four distinct pretraining objectives (MetaCLIP, WebSSL, Cap, CapPa) against a from-scratch encoder under a fixed $1.04 \times 10^{22}$ FLOP lifetime budget:
- Spending up to 15% of lifetime compute on encoder pretraining performed no better than allocating 100% of compute to end-to-end multimodal training.
- When pretraining consumed 60% of lifetime compute, multimodal VQA accuracy collapsed.
- Even when encoder pretraining compute was treated as **free** (zero-cost), the from-scratch encoder remained fully competitive with MetaCLIP.

#### Choice 2: The Fallacy of Encoder-Free Architectures
Proponents of encoder-free models claim that projecting patches directly into a larger unified backbone is optimal. The authors enlarged the encoder-free backbone by the exact parameter count of the encoder (1.7B $\to$ 2.1B):
- **Visual Understanding Trails**: Encoder-free models scored **39.0%** on Average VQA versus **44.4%** for the scratch encoder.
- **Compute Inefficiency**: The encoder-free architecture requires **$3.0\times$ to $4.4\times$ more training FLOPs** to achieve parity with an encoder-augmented model on visual question answering.
- *Reason*: Without dedicated vision parameters, vision tokens and text tokens compete destructively for shared feed-forward network (FFN) capacity, diluting fine-grained perceptual representations.

#### Choice 3: Pre-Fusion vs. In-Fusion Placement
If dedicated vision parameters are required, do they need to reside in a separate pre-fusion Vision Transformer?
The authors reallocated the 0.4B vision parameters directly inside the backbone as **vision-only FFN and attention branches**:
- **Where to Place**: Placing vision-only modules in the **first 8 layers (Layers 1–8)** achieved **45.0% VQA**, matching or slightly exceeding the pre-fusion scratch encoder (**44.4%**).
- Spreading the capacity evenly across all layers (37.6%) or placing it in late layers (35.1%) failed completely.
- *Mechanism*: Vision tokens require specialized processing early, while they are still close to raw patch signals; once fused into abstract semantic representations, shared transformer layers handle multimodal reasoning efficiently.

## Comprehensive Benchmark Results

### 1. Architectural Ablation across VQA and Text Benchmarks
All models evaluate 0.4B dedicated vision capacity paired with a 1.7B backbone at matched $1.04 \times 10^{22}$ FLOP budget:

| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Scratch Encoder** | Dedicated (0.4B) | Pre-Fusion | 44.4 | 57.2 | 35.7 | **38.2** | 46.5 | 49.7 |
| **Encoder-Free** | None (Shared) | — | 39.0 | 50.7 | 35.0 | 25.2 | 45.0 | **50.7** |

*Key Findings*:
- In-Fusion (Early) matches the Pre-Fusion Scratch Encoder across all dimensions and delivers a massive **+10.8 percentage point gain** in OCR/chart understanding over Encoder-Free (36.0% vs. 25.2%).
- Reserving parameters strictly for vision tokens is critical: widening shared FFNs for all tokens yields only 40.1% VQA.

Across the entire scaling trajectory (growing vision capacity proportionally from 0.1B to 1.6B parameters), In-Fusion consistently tracks or outperforms the Pre-Fusion Encoder, while Encoder-Free remains permanently handicapped:

## Practical Implications

1. **Abandon Separate Vision Encoder Pretraining**: Foundation model labs do not need to maintain complex, two-stage pretraining pipelines (e.g., training SigLIP on billions of image-text pairs before training the LLM). End-to-end multimodal joint training from scratch is compute-optimal.
2. **The End of the Two-Model Serving Bottleneck**: Separate vision encoders force serving systems (vLLM, SGLang) to manage two distinct neural network forward passes, pipeline stalls, and cross-model tensor copies. In-Fusion consolidates vision processing into the main transformer graph, dramatically reducing **Time-to-First-Token (TTFT)**.
3. **The Definitive Verdict on Encoder-Free Models**: Pure encoder-free vision modeling (feeding linear patch embeddings into a homogeneous transformer) is fundamentally suboptimal. Perceptual token processing requires dedicated parameter capacity in the initial layers.

## 核心痛点：多模态大模型视觉编码架构的“混杂假说”

多模态大语言模型（MLLM）究竟应当如何摄入视觉图像信息，一直是学术界与工业界最具争议的架构焦点：
- **经典外挂编码器派（如 LLaVA、Qwen-VL、Pixtral）**：采用一个预训练好的独立视觉编码器（如 CLIP、SigLIP、DINOv2），将图像切块提取为视觉 Token，经投影层灌入大语言模型。
- **端到端联合训练派（如 Chameleon、PaLI）**：依然保留独立的视觉 ViT 架构，但放弃外挂预训练检查点，与语言基座从零开始联合训练。
- **无编码器原生派（Encoder-Free，如 Fuyu、Gemma 3）**：彻底扔掉视觉 ViT，直接用一个简单的线性投影层将图像 Patch 映射进统一步长的大语言模型 Transformer 中。

以往业界在评估这三种流派时，往往依据各家已发表开源模型的基准跑分。然而，各家模型在底层预训练数据、文本分词器、模型参数量及总训练算力（FLOPs）上截然不同，**根本无法得出公正的因果归因**。

作者敏锐地指出，**传统的视觉编码器实质上将三个彼此正交的设计决策深度“捆绑”在了一起**：
1. **视觉先验（Visual Prior）**：从上游预训练（如海量图文对比学习）中继承而来的图像表征知识；
2. **专用视觉参数容量（Dedicated Vision Capacity）**：专门分配给视觉 Token、不被文本 Token 争抢的独立模型参数；
3. **融合前置布局（Pre-Fusion Placement）**：这部分视觉处理算力被严格隔离在多模态交互融合层（即图文可以互相 Attention 的第一层）**之前**。

```
                     视觉编码器深度捆绑的三大核心设计维度

  【传统外挂视觉编码器架构 (如 CLIP / SigLIP)】：
  输入图像 ──> [独立预训练 ViT 编码器 (0.4B)] ──> 投影层 ──> [多模态语言模型主干]
               ├─ 1. 是否必须具备上游预训练视觉先验？ (对比学习/分类先验)
               ├─ 2. 是否必须具备专门处理视觉的参数容量？ (0.4B 独立视觉参数)
               └─ 3. 这部分视觉算力是否必须严格置于大模型融合之前？ (完全独立前置)

  核心追问：究竟是哪个因素在真正起作用？我们能否彻底干掉外挂 ViT，实现极简部署？
```

## 核心突破：全生命周期算力对齐下的解构实验

**核心结论**：Meta FAIR 与纽约大学团队（包括 Saining Xie、Luke Zettlemoyer 与 Lucas Beyer 等学术泰斗）建立了首个严格控制变量且**全生命周期算力严格对齐（Lifetime Compute Matched）**的多模态评测体系，得出三大里程碑结论：
1. **预训练视觉先验毫无必要**：在相同总算力下，从零联合训练的编码器与预训练编码器性能完全对齐；
2. **专用视觉参数容量不可或缺**：无编码器（Encoder-Free）方案在 VQA 理解上落后多达 5.4 个百分点，需要多耗费 3 到 4 倍算力才能勉强追平；
3. **视觉算力无需前置隔离**：将专用视觉参数以内置模块形式直接嵌入主模型**前 8 层（In-Fusion）**，不仅精度完美持平独立编码器，更消除了跨模型推理编排，大幅降低首字生成延迟（TTFT）。

```
                        解构多模态视觉编码的三大实验定论

  问题 1：视觉编码器真的需要独立预训练吗？
  【预训练编码器】 vs 【从零联合训练编码器】（严格对齐全生命周期总 FLOPs）
  ──> 结论：从零联合训练全面对齐甚至超越预训练！上游预训练算力不如直接砸给多模态阶段。

  问题 2：视觉编码需要专用参数容量吗？
  【从零编码器 (1.7B + 0.4B)】 vs 【无编码器架构 (统一扩容至 2.1B 主干)】
  ──> 结论：无编码器方案在视觉问答上全面溃败（OCR暴跌13个点，需3.0~4.4倍算力追平）！
            视觉特征必须拥有专属参数，不能与文本共享 FFN 争抢容量。

  问题 3：专用视觉算力必须置于大模型之前吗？
  【前置独立 ViT (0.4B)】 vs 【内置于大模型前 8 层的视觉专属模块 (In-Fusion)】
  ──> 结论：In-Fusion 在所有 VQA 任务上全面超越前置独立编码器！
            不仅彻底消灭了双模型架构，更大幅降低首字响应延迟（TTFT）。
```

## 核心实验机制与架构解构

### 1. 全生命周期算力对齐控制协议
研究者摒弃了外部现成的检查点，所有模型均基于完全相同的语料从零预训练：
- **文本数据**：Nemotron-CC v2/v2.1；
- **多模态图文数据**：MetaCLIP 1.2 英文子集（经 Qwen2.5-VL-32B 全量重打标的高清详细描述）；
- **数据配比**：70% 纯文本，30% 图文交错；
- **生命周期算力计量**：不仅统计多模态训练步数，更将视觉编码器上游预训练所消耗的浮点计算量（FLOPs）严格合并计量。

```
                         四种解构实验路线机制对比表

  架构方案路线           视觉先验 (Prior)   专用视觉容量 (Capacity)  融合前置位置 (Pre-Fusion)
  ─────────────────────────────────────────────────────────────────────────────────────────────
  1. 预训练编码器路线         有                     有                      是 (前置独立 ViT)
  2. 从零训练编码器路线       无                     有                      是 (前置独立 ViT)
  3. 无编码器原生路线         无                     无 (全与文本共享)       否 (线性映射入主干)
  4. In-Fusion 内置路线      无                     有 (专属视觉分支)       否 (嵌入主干前 8 层)
```

### 2. 深入解构三大关键抉择

#### 抉择 1：预训练视觉先验是伪需求
在固定 $1.04 \times 10^{22}$ FLOP 总算力预算下，对比 MetaCLIP、WebSSL、Cap、CapPa 四类主流预训练方案：
- 将生命周期总算力的 7.4% 或 15% 拨给编码器预训练，最终的多模态 VQA 表现与“0% 预训练、全额算力直接从零联合微调”几乎完全一致；
- 一旦预训练算力占比提高至 60%，由于挤占了多模态联合训练步数，模型多模态能力出现剧烈退化；
- 哪怕将编码器预训练算力视作“完全免费（0成本）”，从零联合训练的模型在下游表现上依然与外挂编码器难分伯仲。

#### 抉择 2：无编码器方案的表征塌缩
学术界此前有声音认为：直接把 Patch 线性投影进大模型，省去了 ViT，优雅且通用。作者将无编码器模型的主干扩容 0.4B（使总参数量与“1.7B 主干 + 0.4B 编码器”严格相等）：
- **视觉理解力断崖式下跌**：无编码器模型的 Average VQA 得分仅为 **39.0%**，而拥有独立编码器的模型为 **44.4%**；
- 在 OCR 与图表理解等细粒度感知任务上，无编码器模型跌至 **25.2%**（落后近 13 个百分点）；
- *根本机理*：底层的浅层图像 Patch 包含大量高频空间纹理，强行与高度抽象的高层文本 Token 共享 FFN，会导致严重的参数竞争（Capacity Interference）。

#### 抉择 3：打破融合边界——In-Fusion 早期内置模块
既然视觉必须拥有专属参数，那它必须是一个独立前置的 ViT 吗？
作者将 0.4B 视觉参数以“视觉专属 FFN 分支与视觉注意力投影”的形式内置进大模型主干内部：
- **位置决定成败**：若将视觉专用分支放置在大模型的**前 8 层（Layers 1–8）**，VQA 综合得分达到 **45.0%**，甚至反超了独立前置编码器的 **44.4%**；
- 若将视觉分支分散在所有层（39.4%）或后 8 层（35.1%），效果骤降至与无编码器相当；
- *表征动力学解释*：图像 Token 仅在刚进入模型的早期阶段需要专门的感知特征抽取（从像素走向语义）；一旦完成初步语义抽象，后续层完全可以与文本 Token 深度复用通用推理能力。

## 实践启示与工程落地

1. **废弃繁重的独立视觉预训练工程**：AI 团队无需再花费数周卡时去清洗几亿图文对专门训练 SigLIP 2；直接把视觉 Transformer 挂在大模型上端到端从零开训，不仅省去中间对齐环节，且算力产出比最高。
2. **终结双模型微服务的推理灾难**：以往在 vLLM、SGLang 等推理引擎中部署多模态模型，必须先调用视觉服务运行 ViT，等全部视觉 Token 算完再拷贝进 LLM，导致显存碎片与首字延迟（TTFT）飙升。**In-Fusion 将视觉模块原生融合进 Transformer 计算图**，单次前向直出，大幅压缩 TTFT。
3. **为端侧 MLLM 指明最佳架构**：手机与车载芯片对显存带宽极其敏感。In-Fusion 兼具了“独立编码器的顶级视觉理解力”与“无编码器方案的单网络纯粹架构”，是未来边缘多模态模型迭代的终极形态。
