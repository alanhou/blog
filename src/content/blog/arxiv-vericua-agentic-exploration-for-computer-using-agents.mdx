## The Gap

The emergence of Computer-Using Agents (CUAs)—agents capable of controlling operating systems, web browsers, and mobile devices through mouse clicks, keystrokes, and API calls (e.g., OSWorld, AndroidWorld, WebArena)—has exposed a glaring bottleneck in the AI lifecycle: **how do we reliably verify whether an agent has actually completed its task?**

Accurate verification is not merely an academic benchmarking metric; it is the fundamental ground truth required for **trajectory filtering in synthetic data pipelines, safe human-in-the-loop deployment, and reward modeling in reinforcement learning (RL)**.

Existing verification paradigms suffer from severe structural failures:

1. **Passive Vision-Language Model (VLM) Judges**:
   - Single-pass VLM evaluators inspect captured screenshots or video trajectories.
   - However, digital environments are **partially observable**. Crucial task outcomes (e.g., whether a file was saved in SQLite, whether a background daemon terminated, or whether an off-screen document was corrupted) are completely invisible in screen frames.
   - Consequently, VLM judges frequently hallucinate task completion based purely on superficial UI cues, yielding high false positive rates (up to 28% on OSWorld).

2. **Handcrafted Programmatic Evaluators**:
   - Traditional benchmarks rely on hardcoded Python/Bash scripts that query specific application states or databases.
   - However, writing custom evaluators for thousands of open-ended software tasks requires enormous engineering effort and breaks as soon as application UI layouts or internal storage schemas change.
   - Furthermore, programmatic scripts cannot evaluate offline recorded human trajectories or legacy execution logs where direct runtime machine access is unavailable.

```
  - Cannot query file systems/DBs        - Requires manual code per task
```

## The Increment

**One sentence**: VeriCUA formalizes verification as an autonomous agentic exploration process that synthesizes environment-grounded rubrics, probes both GUI and system code interfaces to gather decisive evidence, and adjudicates task success under rigorous evidence rules.

```
                              VERICUA WORKFLOW

  [Task Instruction g + Context c]
               │
               ▼
      [Rubric Synthesis] ──> Extracts Hard (Must-Have) & Soft (Negative) Requirements
               │
               ▼
     ┌─────────────────────────────────────────────────────────┐
     │           Active Agentic Exploration Loop               │
     │                                                         │
     │   Hypothesis Selection: Pick unresolved requirement r_i │
     │                           │                             │
     │       Action Space A(S): Hybrid GUI & Code Tools        │
     │       ├── GUI: zoom, crop, OCR, read_a11y, screenshot   │
     │       └── Code: find, read_file, sqlite_query, CLI      │
     │                           │                             │
     │       Observation: Extract Attested vs Asserted Evidence│
     └───────────────────────────┬─────────────────────────────┘
                                 │
                                 ▼
                     [Rule-Based Arbitration]
              ┌──────────────────┴──────────────────┐
              ▼                                     ▼
      All Requirements Met?               Corroborating Refutation?
      ──> [SUCCESS]                        ──> [FAIL]
              │
              └── Unsettled / Insufficient Evidence ──> [ABSTAIN]
```

## The Anatomy

### 1. Verification as Active Evidence Gathering

Given a user task instruction $g$, an agent executes trajectory $\tau = [o_0, a_0, \dots, o_T]$ and leaves the environment in post-execution state $s_T$. VeriCUA evaluates whether $g$ was fulfilled using available sources $\mathcal{S} = \{S_1, \dots, S_m\}$, outputting a ternary decision:
$$y \in \{\text{success}, \text{fail}, \text{abstain}\}$$

The verification proceeds through four distinct stages:
1. **Context Inspection**: Probes the operating system environment or recording metadata to construct initial context $c$ (e.g., active window, directory structures, platform type).
2. **Rubric Synthesis**: Uses $g$ and $c$ to synthesize an explicit set of requirements $R = \{r_1, r_2, \dots, r_n\}$, distinguishing **hard requirements** (necessary task completions) from **soft constraints** (side-effect prohibitions, e.g., "no unrelated files modified").
3. **Active Exploration**: At step $k$, the verifier policy $\pi_V$ selects an inspection action $\alpha_k = (v_k, x_k) \in \mathcal{A}(\mathcal{S})$ pairing a tool $v_k$ with arguments $x_k$:
   $$\alpha_k \sim \pi_V(\cdot \mid g, c, R, \mathcal{E}_{k-1})$$
   $$\text{Execute}(\alpha_k, \mathcal{S}) \longrightarrow (\tilde{o}_k, t_k)$$
   where $\tilde{o}_k$ is the returned tool output and $t_k$ represents the evidence type and source metadata tracked by the harness.
4. **Rule-Based Arbitration**: Aggregates the findings record $\mathcal{E}_L$ to adjudicate requirement satisfaction without trusting unaudited model intuitions.

### 2. Hybrid Action Space: GUI + Code State

Unlike prior methods that strictly silo GUI inspection from code inspection, VeriCUA provides a unified action space $\mathcal{A}(\mathcal{S})$:
- **Code Probes (Online Settings)**:
  - `find(path, pattern)`: Scans filesystem hierarchies for generated output files.
  - `read_file(path, offset, length)`: Directly inspects configuration files, scripts, or persistent documents.
  - `sqlite_query(db_path, query)`: Validates database records (e.g., contacts, calendar events, settings tables).
  - `cli_command(command)`: Executes sandboxed commands to inspect running processes or network ports.
- **GUI Probes (Online & Offline Settings)**:
  - `screenshot()`, `get_frame(t)`: Captures live desktop screens or temporal video frames.
  - `zoom(box)`, `crop(box)`: Zooms in on high-density UI elements (e.g., small checkboxes or fine text).
  - `ocr(box)`: Extracts localized optical character recognition tokens.
  - `read_a11y()`: Dumps structured accessibility trees to parse exact UI widget states.

### 3. Strict Evidence Discipline: Attested vs Asserted Evidence

A primary driver of VLM judge error is conflating an agent's **intent** with **actual environment state**. VeriCUA introduces an explicit evidence typology:
- **Asserted Evidence**: The agent's natural language thoughts, pre-action planned tool calls, or completion claims ("I have successfully changed the brightness"). Asserted evidence can propose hypotheses for exploration but **can never alone satisfy a hard requirement**.
- **Attested Evidence**: Verified physical facts verified via independent sensors—a filesystem byte match, an SQL record timestamp, or a post-execution cropped UI element.

To mark a requirement $r_i$ as `met`, VeriCUA requires attested support. Conversely, marking a requirement `unmet` requires corroborating refutations across multiple probes to avoid false negatives due to minor tool syntax variations.

## Key Takeaways

1. **Verification is an Active Investigation, Not a Forward Pass**: Passing an entire trajectory or final screenshot into a single LLM prompt fails because digital environments conceal state changes beneath superficial pixels. Active exploration is essential.
2. **Hybrid Probing is Essential**: Combining code-based filesystem checks with visual OCR/a11y checks resolves ambiguities that neither modality can solve alone. GUI checks confirm visual intent; code checks confirm data persistence.
3. **The Value of Abstention**: In automated RL fine-tuning and synthetic dataset curation, admitting ignorance (`abstain`) is far superior to asserting a false positive. By withholding judgment when evidence is ambiguous, VeriCUA delivers curated datasets with clean reward signals.

## 核心痛点与背景

随着计算机操作智能体（Computer-Using Agents, CUAs）在桌面（OSWorld）、移动端（AndroidWorld）以及网页端（WebArena）的快速发展，智能体已具备通过键鼠模拟和系统调用完成复杂长程任务的能力。然而，AI 社区面临着一个致命的底层瓶颈：**我们如何可靠、自动化地验证智能体是否真正完成了任务？**

任务完成度验证不仅是基准评测的核心，更是**合成训练数据清洗、强化学习（RL）自动化奖励标注、以及安全部署保障**的生命线。

现有的评测范式存在根本性的结构缺陷：

1. **被动式多模态大模型（VLM）裁判的“局部观测幻觉”**：
   - 现存方案通常将执行过程的视频截图或最终屏幕画面喂给 VLM 进行单次打分判断。
   - 然而，真实的操作系统环境具有极强的**部分可观测性（Partial Observability）**。例如：文件是否按正确编码写入了 SQLite、后台守护进程是否已安全退出、屏幕未展示区域的数据是否被意外破坏等，在静态截图中均完全不可见。
   - 这导致 VLM 裁判极易被表面的 UI 视觉假象所欺骗，在 OSWorld 等真实系统任务中产生高达 27.9% 的严重假阳性率（False Positive Rate）。

2. **硬编码测试脚本（Programmatic Evaluators）的“脆弱性困境”**：
   - 传统基准测试依赖人工编写 Python/Bash 脚本探测数据库或系统状态。
   - 为成千上万个开放式真实任务编写独立评测脚本成本极其高昂，且一旦应用软件升级、UI 布局微调或存储路径改变，硬编码脚本便大面积失效。
   - 此外，测试脚本无法应用于离线记录的人类或智能体轨迹（Recorded Trajectories），适用场景受限。


## 核心技术实现

### 1. 探索式证据搜集模型

对于给定的自然语言任务 $g$，智能体执行轨迹 $\tau = [o_0, a_0, \dots, o_T]$ 并将操作系统留在最终状态 $s_T$。VeriCUA 在任务结束时刻启动，根据可用数据源 $\mathcal{S}$ 输出三元判定：
$$y \in \{\text{success}, \text{fail}, \text{abstain}\}$$
引入“弃权（abstain）”机制对于构建高纯度的强化学习训练集至关重要，避免在证据模糊时产生误导性奖励。

VeriCUA 包含四大执行阶段：
1. **上下文嗅探（Context Inspection）**：先期探测机器环境元数据（当前活动窗口、桌面架构、已安装软件、文件目录树等），构建上下文 $c$。
2. **规约合成（Rubric Synthesis）**：将任务 $g$ 转化为机器可逐项验证的规约集合 $R = \{r_1, \dots, r_n\}$。严格区分**硬性完成条件（Hard Requirements）**与**软性约束条件（Soft Constraints，如不得破坏无关用户数据）**。
3. **主动探索探测（Active Exploration）**：在第 $k$ 步，验证策略网络 $\pi_V$ 调度工具动作 $\alpha_k = (v_k, x_k) \in \mathcal{A}(\mathcal{S})$：
   $$\alpha_k \sim \pi_V(\cdot \mid g, c, R, \mathcal{E}_{k-1})$$
   $$\text{Execute}(\alpha_k, \mathcal{S}) \longrightarrow (\tilde{o}_k, t_k)$$
   底层测试沙箱（Harness）执行探测并标记数据源属性与时间戳元数据。
4. **规则化仲裁（Rule-Based Arbitration）**：摒弃端到端黑盒评分，根据收集到的确凿事实链按照严格的布尔规则实施仲裁。

### 2. 混合动作空间（Hybrid Action Space）

VeriCUA 彻底打破了“视觉流”与“代码流”的割裂：
- **系统代码工具（用于在线环境）**：
  - `find(path, pattern)`：在文件系统层级递归定位生成目标。
  - `read_file(path, offset, length)`：读取配置与文本内容，杜绝 UI 渲染截断带来的误判。
  - `sqlite_query(db_path, query)`：核验本地结构化数据库（如备忘录、通讯录、系统偏好设置）。
  - `cli_command(command)`：以受控权限执行诊断命令。
- **GUI 交互工具（同时支持在线实机与离线轨迹）**：
  - `screenshot()` / `get_frame(t)`：捕获实时屏幕或历史帧。
  - `zoom(box)` / `crop(box)`：对密集界面关键区域（如极小状态指示灯或提示语）局部放大。
  - `ocr(box)`：提取局部光学文字。
  - `read_a11y()`：解析无障碍服务辅助树（Accessibility Tree），直接读取控件精确语义。

### 3. 严格的证据法则：断言证据 vs 确证证据

模型裁判误判的关键根源在于将智能体的“自称或计划”当作了“执行结果”。VeriCUA 在工程上严格划分了证据等级：
- **断言证据（Asserted Evidence）**：智能体在轨迹中输出的自然语言思考、计划调用、或者结束时的自我汇报（“我已经把文件保存好了”）。断言证据仅能用于启发探索方向，**绝对不可作为条件判定的通过依据**。
- **确证证据（Attested Evidence）**：由外部测试工具独立测得的不可篡改事实——如磁盘文件字节比对成功、数据库写入时间戳匹配、或动作执行后独立捕获的高清切片。

只有当某条规约获得充分的确证证据支持时才会被标记为 `met`；而标记为 `unmet` 则需要多个独立探测互相印证，以防由于智能体微小的非预期行为产生误杀。

## 启示与实践意义

1. **评测本身即是智能体任务**：过去的评测把大模型当作静态函数使用，面对具有深层状态的复杂操作系统，必须给予评测器动态交互的工具与自由度，让其像一名“侦探”一样主动求证。
2. **GUI 与系统代码的跨模态互补**：视觉观察能快速验证用户体验与控件焦点，而系统底层代码与数据库检查能确证持久化状态。两者结合是杜绝幻觉的唯一正解。
3. **“理性弃权”在 RL 闭环中的巨大价值**：在智能体自动化强化学习飞轮中，错误的高奖励（假阳性）会迅速导致策略退化（Reward Hacking）。VeriCUA 宁可弃权也不给假阳性打高分，为智能体进化提供了极高信噪比的监督信号。
